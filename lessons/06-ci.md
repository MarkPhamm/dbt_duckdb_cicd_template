# Lesson 06 — Slim CI on a real pull request

**Goal:** change `stg_payments` on a branch, open a PR, and watch the
Lesson 04 command run on a runner.

`ci.yml` is already in the repo. Today you open it, then you use it.

Prereq: `cd.yml` has one green run on `main`. No CD artifact, no Slim
CI. That was Lesson 05's checkpoint. If you skipped the run, go press
**Run workflow** now and wait for green.

---

## 1. Two snapshots, not one

The runner is holding two different moments in time. That is the whole
trick.

| Snapshot | Where it comes from | What it is |
|---|---|---|
| The new code | `actions/checkout` of the PR | today's `stg_payments.sql` |
| Last night's prod | the CD artifact | old checksums + prod tables |

`state:modified+` diffs the new code against the old checksums.
`--defer` reads the old tables for everything you did not build.

The wrong picture: *"CI checks out `main` and runs dbt."*

Then the new file is not on the machine. There is nothing to diff.
Checkout is the PR. The artifact is `main` as of last night. Mix those
up and Slim CI is either a no-op or a full rebuild.

Take `stg_payments`. You added a comment on a branch.

| Question | Answer | Who answers |
|---|---|---|
| Did the file change? | yes. checksum moved. | `state:modified` vs the artifact manifest |
| What else could break? | `int_order_payments`, `orders`, `customers` | the `+` |
| Where is `stg_orders`? | `staging.stg_orders`, inside the downloaded `.duckdb` | `--defer` |
| Where do the four new models go? | `ci_pr_42` | `--target ci` + `DBT_CI_SCHEMA` |

Same three flags as Lesson 04. The YAML only fetches the two boxes and
sets the schema name.

---

## 2. When it runs

Open `.github/workflows/ci.yml`.

```yaml
on:
  pull_request:
```

A PR opened, updated, or reopened. That is CI.

Not `push` to `main`. That is `cd.yml`. A merge is too late to prove
the change.

`permissions.actions: read` is not decoration. The download step calls
`gh run list` / `gh run download` against *another* workflow's
artifacts. The default token cannot see those without `actions: read`.
Checkout only needed `contents: read`. Two permissions, two jobs.

---

## 3. A schema per pull request

```yaml
DBT_CI_SCHEMA: ci_pr_${{ github.event.pull_request.number }}
```

`profiles.yml` already waits for that variable:

```yaml
ci:
  schema: "{{ env_var('DBT_CI_SCHEMA', 'ci_local') }}"
```

On your laptop the default is `ci_local`. On the runner, PR `#42`
writes `ci_pr_42`. PR `#43` writes `ci_pr_43`.

| PR | Schema | Collision? |
|---|---|---|
| `#42` edits `stg_payments` | `ci_pr_42` | no |
| `#43` edits `stg_orders` | `ci_pr_43` | no |

The wrong fix: drop the variable and let every PR use `ci_local`.

Then `#43` overwrites `#42`'s tables mid-run. Two dress rehearsals,
one stage. Lesson 02 made you create `ci_pr_42` by hand for this
reason. The workflow just sets the name.

Both PRs still download the *same* prod `.duckdb`. They add their own
schema next to `staging` / `marts`. They do not rebuild prod.

---

## 4. Opening the boxes

This is the only new mechanic. Artifacts live on the run that uploaded
them. `cd.yml` uploaded. `ci.yml` is a different run. Nothing shows up
for free.

The wrong tool: `actions/download-artifact` with no run id.

That action, by default, only sees artifacts from *this* workflow run.
CI never uploaded any. Empty folder. Then `--state` has no manifest,
or `--defer` has no tables.

So we go get last night's CD run by hand:

```bash
RUN_ID=$(gh run list \
  --workflow=cd.yml \
  --branch=main \
  --status=success \
  --limit=1 \
  --json databaseId \
  --jq '.[0].databaseId')
```

Latest successful `cd.yml` on `main`. Not a failed run. Not a run from
this PR.

If that id is empty, we exit. You have seen the message:

```
No successful cd.yml run on main yet.
```

Then:

```bash
gh run download "$RUN_ID" --name prod-dbt-artifacts --dir prod_dbt_artifacts
cp prod_dbt_artifacts/database.duckdb database/database.duckdb
```

| File in the artifact | Lands at | Used by |
|---|---|---|
| `manifest.json` | `prod_dbt_artifacts/manifest.json` | `--state` / `state:modified+` |
| `database.duckdb` | `database/database.duckdb` | `--defer`, and CI writes `ci_pr_42` into this same file |

Two names, still one idea. GitHub's artifact is `prod-dbt-artifacts`.
The folder `--state` reads is `prod_dbt_artifacts/`. The copy is
because `profiles.yml` says `path: database/database.duckdb`. Defer
looks inside that file for `staging.stg_orders`. The new models land
in the same file, in a different schema.

---

## 5. The command you already know

```yaml
uv run dbt build --target ci
  --select state:modified+
  --defer --state prod_dbt_artifacts/
```

That is Lesson 04, line for line. `--target ci` plus `DBT_CI_SCHEMA`
is the only difference from your laptop: the schema is `ci_pr_42`,
not `ci_local`.

Take `orders` again.

| `ref()` | Selected? | Resolves to |
|---|---|---|
| `int_order_payments` | yes | `ci_pr_42.int_order_payments` |
| `stg_orders` | no | `staging.stg_orders` (inside the downloaded prod file) |

Without `--defer` this dies the same way it died on your laptop:
`ci_pr_42.raw_payments` does not exist. The YAML does not save you.
The flag does.

## 6. Do it

On `main`, CD is green. Then:

```bash
git checkout -b lesson-06-stg-payments
echo "-- experiment" >> models/staging/stg_payments.sql
git add models/staging/stg_payments.sql
git commit -m "Experiment: touch stg_payments so Slim CI has something to select."
git push -u origin HEAD
gh pr create --title "Lesson 06: slim CI" --body "Throwaway. Close after the check goes green."
```

GitHub → the PR → **Checks** → **ci**.

You want four models, then tests:

```
OK created sql view model ci_pr_N.stg_payments
OK created sql view model ci_pr_N.int_order_payments
OK created sql table model ci_pr_N.orders
OK created sql table model ci_pr_N.customers
Done. PASS=16 ERROR=0
```

`stg_customers` and `stg_orders` are not in that list. They were not
selected. `--defer` read them from prod. Same four-of-six as Lesson 03.

A docs-only PR (you only edited a markdown file) is also green, and
builds **zero** models. That is not a bug. `state:modified+` found
nothing. Slim CI stayed slim.

Close the PR. Do not merge the experiment comment.

```bash
git checkout main
git restore models/staging/stg_payments.sql   # if it is still dirty locally
```

`git restore` discards every uncommitted change to that file. If you
already committed on the branch, leave `main` clean and delete the
branch after you close the PR.

## 7. The loop, once a real PR merges

A real change, not an experiment, goes through both files:

```
  open PR   ──> ci.yml  ──> prove stg_payments + downstream
  merge     ──> cd.yml  ──> rebuild everything
                      └──> upload a new artifact
  next PR   ──> ci.yml  ──> diffs against *that* artifact
```

Tomorrow's CI does not compare against the PR you just closed. It
compares against the CD run that landed on `main`. Merge a broken
model and CD goes red too — and the next PR has no new successful
artifact, so it keeps diffing yesterday. That is why CD must finish.

---

Tiny mental model: the PR is today's script. The artifact is last
night's recording. Slim CI plays the new scene against the old set.
It does not rebuild the theatre.

---

## Checkpoint

1. On the runner, which snapshot is the checkout, and which is the
   artifact? If you swapped them, what would `state:modified+` do?

2. Two PRs are open. Someone deletes `DBT_CI_SCHEMA` so both write
   `ci_local`. What goes wrong, and which lesson already showed you
   the fix?

3. A teammate replaces the `gh run download` block with
   `actions/download-artifact` and no run id. The next PR goes red
   before `dbt build`. Why?

4. You open a PR that only edits `lessons/06-ci.md`. CI is green
   and built nothing. Is Slim CI broken?

---

## Where this leaves us

The two files now do the two jobs.

```
  merge to main ──> cd.yml ──> dbt build --target prod
                                      └──> upload the two boxes

  open a PR     ──> ci.yml ──> open those boxes
                                      └──> dbt build --target ci \
                                             --select state:modified+ \
                                             --defer --state prod_dbt_artifacts/
```

Nothing here stops you typing `--target prod` on your laptop, or
merging a red PR. Lesson 07 is the guardrails.
