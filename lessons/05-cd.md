# Lesson 05 — Your first workflow: CD

**Goal:** put last night's production run on a runner, and leave behind
the two files tomorrow's pull request needs.

Two workflow files. Two jobs. Same names as Lesson 00.

| File | Job | When it runs |
|---|---|---|
| `.github/workflows/cd.yml` | CD — build everything, save artifacts | merge to `main` |
| `.github/workflows/ci.yml` | CI — Slim CI against those artifacts | a pull request |

Today is `cd.yml`. `ci.yml` is already in the repo so the pair exists.
You will open it in Lesson 06. Do not start there.

---

## 1. Two jobs, two files

The wrong picture: *one* `cicd.yml` that does everything.

CI and CD fail differently. They write to different places. They run at
different times. Mixing them in one file hides that.

Take `stg_payments`. You merge a PR that changed it.

| | `cd.yml` | `ci.yml` |
|---|---|---|
| Trigger | push to `main` | `pull_request` |
| Command | `dbt build --target prod` | `dbt build --target ci --select state:modified+ --defer --state ...` |
| What it builds | everything | the change, plus downstream |
| Where it writes | `staging` / `marts` | `ci_pr_42` |
| What it leaves behind | `manifest.json` + `database.duckdb` | a red or green check |

`--target prod` is the CD *target*. `cd.yml` is the CD *file*. The
target is where dbt writes. The file is when a runner bothers to do it.

---

## 2. The laptop command, unchanged

You have already run CD. Lesson 02:

```bash
uv run dbt build --target prod
```

That is the whole job. `cd.yml` is a trigger, an install, that command,
and a save. Nothing in the YAML is a new dbt idea.

Open `.github/workflows/cd.yml`. Walk it top to bottom.

---

## 3. When it runs

```yaml
on:
  push:
    branches: [main]
  workflow_dispatch:
```

`push` to `main` is "someone merged." That is CD.

`workflow_dispatch` is a button in the Actions tab. You need it once:
there is no artifact until the first CD run succeeds. CI cannot start
from nothing. Press **Run workflow** after you push this file if you do
not want to wait for a real merge.

The wrong trigger: `pull_request`.

That would run `dbt build --target prod` from a branch that is not
merged. A draft PR would write production. CD is opening night. It
does not start at the read-through.

`ci.yml` is the file with `on: pull_request`. Different file, on
purpose.

---

## 4. Same dbt as your laptop

```yaml
- uses: astral-sh/setup-uv@v6
  with:
    enable-cache: true
    python-version: "3.12"

- run: uv sync --frozen
```

`--frozen` installs exactly what `uv.lock` says. Same pin as Lesson 01.
If the lockfile and `pyproject.toml` disagree, the job fails instead of
quietly resolving a newer dbt.

`DBT_PROFILES_DIR: .` points at the committed `profiles.yml`. The runner
has no `~/.dbt`. DuckDB has no password, so the file can live in the
repo. On Snowflake this block stays; only the secrets move to GitHub
Secrets. Lesson 08.

---

## 5. Two outputs. Upload both.

```bash
uv run dbt build --target prod
```

still produces two things. The runner throws the machine away when the
job ends. If you do not save them, tomorrow's CI has nothing to
download.

| File | In git? | In the artifact? | Why |
|---|---|---|---|
| `stg_payments.sql` | yes | no | source code; the checkout already has it |
| `target/manifest.json` | no | yes | checksums + prod addresses |
| `database/database.duckdb` | no | yes | the actual prod tables |
| compiled SQL | no | no | CI will compile again |

The `.duckdb` file is a DuckDB tax. On Snowflake the tables already
live in the warehouse. You would upload the manifest only. Here the
warehouse *is* a file, and the file is gitignored, so CD has to carry
it. Lesson 08 takes the training wheel off.

```yaml
- run: |
    mkdir -p prod_dbt_artifacts
    cp target/manifest.json prod_dbt_artifacts/manifest.json
    cp database/database.duckdb prod_dbt_artifacts/database.duckdb

- uses: actions/upload-artifact@v4
  with:
    name: prod-dbt-artifacts
    path: prod_dbt_artifacts/
```

Two names, one idea. The GitHub artifact is `prod-dbt-artifacts`
(hyphens; GitHub's name). The folder `--state` reads is
`prod_dbt_artifacts/` (underscores; the path from Lessons 03–04).
`ci.yml` downloads the first into the second.

Do not commit either file. `prod_dbt_artifacts/` is gitignored on
purpose. The point is they come from the last real CD run.

---

## 6. What we did not slim

Someone will ask: *"Why doesn't CD use `state:modified+` too? Faster."*

Because production has to be complete. A seed refresh, a full-refresh
model, a downstream that CI never built — CD is the run that makes
`marts.customers` true.

CI proves a change. CD applies the project.

| Job | Selector | Why |
|---|---|---|
| CD | none. everything. | the warehouse and the manifest must describe the whole project |
| CI | `state:modified+` | prove the PR, do not rebuild the warehouse |

`concurrency.group: cd` and `cancel-in-progress: false` mean two
merges in a row both finish. Cancelling a prod build mid-upload leaves
CI reading an older artifact, or none.

---

## 7. Run it

The file is in the repo. Push `main` (or press **Run workflow**).

```bash
git add .github/workflows/cd.yml .github/workflows/ci.yml
git commit -m "Add the CD and CI workflows."
git push
```

Then GitHub → **Actions** → **cd**.

A green run is not the interesting part. Open it. Download
`prod-dbt-artifacts`. You should see exactly two files:

```
manifest.json
database.duckdb
```

That is the handshake from Lesson 00. CD wrote it. CI will read it.

If Actions is disabled on the repo, enable it once under Settings →
Actions.

`ci.yml` will fail on a pull request until this has succeeded once.
That is not a bug. No CD artifact, no Slim CI.

---

Tiny mental model: `cd.yml` is last night's show, boxed up.
`manifest.json` is the programme. `database.duckdb` is the set.
`ci.yml` is tomorrow's rehearsal, opening those two boxes.

## Checkpoint

1. A teammate adds `pull_request:` to `cd.yml` "so we can test the prod
   build on the PR." What does that actually write to, and why is that
   the wrong file to change?

2. CD uploads `database.duckdb` as well as `manifest.json`. Which of
   those does `state:modified` need? Which does `--defer` need? Why
   does DuckDB force you to upload both?

3. You never run `cd.yml`. You open a PR. What happens in `ci.yml`,
   and why?

4. Why is `uv sync --frozen` in the workflow, not a plain `pip install
   dbt-core`?

